# `diffo` Security & Quality Audit — Final Report

## 1. Executive Summary

`diffo` builds cleanly and passes its full test suite on Zig 0.16.0 with zero compiler diagnostics. The code is well-structured and the happy paths are correct, but the audit surfaced a dense cluster of **memory-ownership defects (22 of 64 findings)** concentrated in two areas: the snapshot-load/teardown sequence in `cli.zig`/`git.zig`, and the comment/state persistence paths in `store.zig`. The single critical issue is a use-after-return on the universal keystroke path. The remaining high-severity issues are double-frees and one parser crash, almost all gated behind error paths (write failure, OOM, corrupt store, malformed patch) rather than the happy path — real memory-safety defects, but mostly bounded to a crash on an already-failing operation.

**Top risks by name:**
1. **[F1]** `readEvent` returns a slice into its own stack frame (use-after-return on every keystroke).
2. **[F2–F4, F7, F8]** `loadSnapshot` move-then-double-free family (`cli.run` + `loadDefaultContext`).
3. **[F5/F10]** `addComment` errdefer double-frees a comment already owned by `self.comments`.
4. **[F9]** Malformed second `@@` header double-frees a flushed hunk in `parsePatch`.
5. **[F6]** Double-free of the source buffer when `syntax_query.build()` fails.

**Severity counts:** Critical 1 · High 10 · Medium 11 · Low 42 (total 64).
**Dimension counts:** memory 22 · robustness 17 · simplicity 13 · correctness 7 · performance 4 · ffi 1.

## 2. Build & Tests

- **Builds:** Yes. `zig build` exits 0 with no errors, warnings, or notes; produces `zig-out/bin/diffo` (~17 MB). All vendored tree-sitter C grammars (core lib plus zig/javascript/typescript/tsx/rust/c/cpp/python/gn, `build.zig:49-88`) compile cleanly.
- **Tests:** Yes. `zig build test` exits 0 with no output, running both module tests (`src/root.zig`) and executable tests (`src/main.zig`) per `build.zig:34-46`. Zig emits output only on failure, so clean exit confirms all tests passed.
- **Notable diagnostics:** None captured. Note: the C-grammar compile was served from a warm `.zig-cache`, not rebuilt from scratch, so first-build grammar warnings (if any) were not re-observed.
- **Coverage gap worth flagging:** several confirmed defects (`mergeOrAppendFile` leaks/double-free, `addComment` error paths, `readEvent`) have **no test coverage** — they require a live TTY, an injected failing allocator, or a merge fixture the suite never exercises. This is why the testing allocator never flagged them.

## 3. Findings

### Critical

**[F1] `readEvent` returns a slice into its own stack frame (use-after-return)** — `src/tui.zig:2320-2327` _(memory)_
`readEvent` declares `var buf: [64]u8 = undefined;` on its own stack, reads stdin into it, then returns `Event{ .key = buf[0..n] }`. `Event.key` is a `[]const u8` fat pointer (tui.zig:91-94), so the returned union carries a pointer into a frame that is reclaimed on return; `handleEvent` then overlaps that frame and dereferences `key[0]`, `key.len`, `std.mem.eql(key, …)`, `key[1]`. Every keystroke takes this path, so it is exercised on completely normal use; it "works" only by accident of stack layout. The mouse path is safe because `parseSgrMouse` copies scalar fields out. (Verifiers split on critical-vs-high since impact is a bounded read of a ≤64-byte region the program just owned — garbled/dropped keystrokes rather than exploitable corruption — but it is universally reached UB and must not depend on inlining.)
**Fix:** Do not return a slice into a function-local buffer. Hoist the input buffer into `run()`'s frame and pass it in (`fn readEvent(buf: *[64]u8) ?Event`, returning slices of the caller-owned buffer), or have `readEvent` fill a caller-provided buffer and return the length, constructing the `Event` in `run()`.

### High

**[F2 / F3 / F8] Double-free of `repo`/`target` on any error after `loadSnapshot` in `cli.run`** — `src/cli.zig:27-37` _(memory)_
_F2, F3, and F8 are the same finding for the `run()`/`mainImpl` path and are merged here._ `errdefer target.deinit` (28) and `errdefer repo.deinit` (30) stay armed after `git.loadSnapshot` (31) takes both **by value** and stores shallow copies into the snapshot (`git.zig:166-167` — same heap pointers, no dupe). With `defer snapshot.deinit` (32) also covering them, any later error — `Store.init` returning `StorageWriteFailed`/`StorageCorrupted` (33), `defaultAuthor` OOM (35), or `tui.run` propagating a write failure during interactive `r`/`c` (37) — runs `snapshot.deinit` *and* the two still-armed errdefers, freeing `root_path`/`repo_id`/`current_branch`/`normalized_spec`/`target_id` twice. Triggers are concrete and not OOM-only (e.g. unwritable `XDG_STATE_HOME`, corrupt `comments.json`, read-only FS during a review action).
**Fix:** Once `loadSnapshot` succeeds the snapshot owns `repo`/`target` — drop the `errdefer repo.deinit`/`errdefer target.deinit` and rely solely on `defer snapshot.deinit`. Guard the pre-`loadSnapshot` window with a `moved` flag or by restructuring so `repo`/`target` are consumed immediately. Alternatively make `loadSnapshot` dupe its inputs so ownership is never shared.

**[F4 / F7] Double-free of `repo`/`target` on `Store.init` failure in `loadDefaultContext`** — `src/cli.zig:220-228` _(memory)_
_F4 and F7 are duplicates and are merged._ Same move-then-double-free as F2, but worse: `errdefer target.deinit` (222), `errdefer repo.deinit` (224), and `errdefer snapshot.deinit` (226) are **all** simultaneously armed. If `Store.init` (227) returns `StorageCorrupted` (malformed `comments.json`/`review-states.json`) or `StorageWriteFailed` (state dir uncreatable), all three fire on the same five pointers. Reached by every JSON/agent subcommand — `comments list/get/add/clean`, `review status/mark` (cli.zig:53,63,100,130,164,181) — so a corrupt or unwritable local store double-frees on a normal error. (One verifier noted the F4/F7 preamble claim that `run()` shares this *exact* triple-errdefer shape is inaccurate; the `run()` variant is F2/F3/F8 above with `defer snapshot.deinit`, not `errdefer`.)
**Fix:** After `loadSnapshot` succeeds, remove the `errdefer target.deinit`/`errdefer repo.deinit` so only `errdefer snapshot.deinit` covers them; keep per-value errdefers only to guard the window before `loadSnapshot` consumes them.

**[F5 / F10] `addComment` errdefer double-frees a comment already owned by `self.comments`** — `src/store.zig:228-238` _(memory)_
_F5 and F10 are the same finding and are merged._ `errdefer comment.deinit(self.allocator)` (228) stays live to function end. `list.append(comment)` (233) copies the struct by value (sharing its owned slice fields) and `toOwnedSlice` (235) commits it into `self.comments[last]`. If `saveComments()` (236) returns `StorageWriteFailed` (full/read-only disk, rename failure) or `cloneComment` (237) OOMs, the errdefer frees `comment`'s 14 string fields — which `self.comments[last]` still aliases — and a subsequent `store.deinit()` (via `defer context.deinit()` / the TUI `c` path) frees them again. Reachable from `diffo comments add` and the TUI add-comment flow.
**Fix:** Cancel/transfer ownership before the fallible ops: build the clone first (so only the return value needs an errdefer), then move `comment` into the list last, and do not keep an errdefer on `comment` past the `toOwnedSlice` assignment (or guard it with a `committed` flag set just before commit).

**[F6] Double-free of `source` buffer when `syntax_query.build()` fails** — `src/syntax_cache.zig:80-83` _(memory)_
`get()` registers `errdefer self.allocator.free(source)` (81), then passes `source` into `build()` (83), which registers its **own** `errdefer allocator.free(source)` (syntax_query.zig:43). Any error from `build()` after line 43 — `TreeSitterParseFailed` (parse returns null), or `Allocator.Error` from `buildLineStarts`/`alloc`/`toOwnedSlice` mid-build — frees `source` in `build`, propagates through the `try`, and frees it again in `get`. Realistic triggers are parse-returns-null on pathological input and mid-build OOM on a sub-512KB file (the static bundled grammars make `TreeSitterQueryInvalid`/`LanguageRejected` effectively unreachable). Secondary leak on the same line: if `entries.append()` (84) OOMs after a successful build, `get`'s errdefer frees only `source` and leaks `highlight.line_starts`/`spans_by_line` (see also F59).
**Fix:** `build()` already owns and frees `source` on its error paths, so `get()` must not double-register. Remove the line-81 errdefer and free `source` explicitly only in the pre-build `SourceTooLarge` early return; on `entries.append` failure, deinit the full `highlight` (which frees `source` too).

**[F9] Malformed second `@@` header double-frees a flushed hunk in `parsePatch`** — `src/diff.zig:292-312` _(memory)_
On a second/later `@@` header the previous hunk's `header` is moved into `hunks` via `append` and `current_lines` is reset, but `current_header` is **not** nulled (unlike the final flush at diff.zig:367). If the very next `parseHunkHeader(line) orelse return error.ParseFailed` (305) fails on a malformed header (e.g. `@@ -bogus +1 @@`), the errdefer (238-246) frees `current_header` *and* frees the same header again via `for (hunks.items) |*hunk| hunk.deinit`. Reproduced: feeding `parsePatch` (public API, fed `git diff` stdout) a patch with a valid first hunk then a malformed second header segfaults inside `Allocator.free`. Reachable via truncated/corrupt git output or any caller passing arbitrary patch text. (One verifier rated this medium given Debug's allocator detects it as a deterministic panic and git itself never emits such headers; it remains a genuine heap corruption on a public parser.)
**Fix:** Add `current_header = null;` immediately after `current_lines = .empty;` (line 303), mirroring the correct final-flush at line 367.

**[F11] Oversized files (>512KB) re-spawn git and re-read the whole blob for every visible line on every frame** — `src/syntax_cache.zig:74-90` _(performance)_
`get()` memoizes only **successful** builds: it calls `git.loadFileSide()` (80) — which spawns `git show` (or reads the worktree file up to 4MB) and loads the entire blob — *before* the `if (source.len > max_file_size) return error.SourceTooLarge` at line 82, which is before the `entries.append` at 84. Nothing is cached, so for any file side >512KB in a grammar-supported language, every visible code line (in split mode, per side) on every `render()` (i.e. every keypress) re-spawns git and re-reads the full blob, then discards it — making scrolling such files effectively unusable. (Verifiers note the conjunctive precondition — size >512KB AND a registered grammar — narrows the trigger, putting it at the high end of the high/medium boundary; impact is severe jank, not a crash.)
**Fix:** Cache negative outcomes. Store a per-`(file_index, side)` status (`Ready`/`TooLarge`/`Unavailable`, or an optional highlight) so a too-large or unavailable side is loaded at most once; at minimum append a sentinel entry on the `SourceTooLarge`/`SyntaxUnavailable` paths so subsequent `get()` calls short-circuit.

### Medium

**[F12] Unreadable untracked file aborts the entire snapshot load** — `src/git.zig:210-216` _(robustness)_
`appendUntrackedPatch` maps every `readFileAlloc` error except `StreamTooLong` to a fatal `error.GitCommandFailed`, which propagates up through `loadSnapshot` and aborts diffo with a generic "git command failed". Common repo states trigger it: an untracked broken symlink (`FileNotFound`), a no-read-permission untracked file (`AccessDenied`), or an untracked nested repo/directory entry from `ls-files` (`IsDir`). One bad entry kills the whole review even though every other file is fine; `readWorktreeFile` (git.zig:514-517) deliberately tolerates these, proving the inconsistency is unintended. (Verifiers split high/medium; the broken-symlink/permission legs are common enough that one rated it high.)
**Fix:** Treat per-file read failures as "skip this untracked file": handle `FileNotFound`/`AccessDenied`/`IsDir` (and ideally any non-OOM open error) by `return;`, propagating only `OutOfMemory`. Optionally emit a binary-placeholder patch for `IsDir` so the entry stays visible.

**[F13] `fitCell` mishandles non-SGR escape sequences and bare ESC bytes** — `src/tui_text.zig:14-21` _(robustness)_
The ANSI handler assumes every escape is an SGR sequence terminated by `'m'` (`while (i < text.len and text[i] != 'm')`). For any non-SGR escape (`\x1b[K`, `\x1b[2J`, cursor moves) or a bare `\x1b`, the scan runs to the next stray `'m'` or end-of-string, swallowing visible chars as zero-width (over-padding/overflow) and re-emitting the raw control sequence into a rendered cell where the terminal executes it. Reachable via raw ESC bytes in untracked file paths (`git ls-files -z` emits them literally) flowing to `fitCell` at tui.zig:1563/415. (One verifier found the cited `file.path`/comment vectors are guarded under default `core.quotePath=true` and the comment editor strips ESC, so practical exploitability via those callers is limited — but the latent function-level bug is real and the same flawed scanners are duplicated at tui.zig:823-829 and 908-912.) The fix's reference to tui.zig:2522-2530 is misdirected — that is the input parser, not a render scanner.
**Fix:** Parse CSI properly: after `\x1b[`, consume parameter/intermediate bytes and stop at the final byte, treating the whole thing as zero width; preserve only `'m'`-terminated SGR for styling. Bound the scan so a lone ESC cannot swallow the rest of the string. Mirror the fix in the duplicated scanners at tui.zig:823-829 and 908-912.

**[F14] Tabs and control bytes counted as zero display width, overflowing the layout** — `src/tui_text.zig:42-61` _(correctness)_
`displayWidth` returns 0 for any byte `< 0x20`, including TAB. `fitCell` emits the raw `\t` while advancing `visible` by 0, then pads to `width` as if the tab took no space; a real terminal advances to the next tab stop, so the cell renders wider than `width` and corrupts alignment (comment-editor right border at tui.zig:3012-3013, status bar, file-tree path). Trigger is unconditional via the comment editor's Tab key (tui.zig:2544); git paths with raw tabs are a secondary vector. Impact is a transient visual/border misalignment, not data loss — the stored comment body is correct.
**Fix:** Expand tabs to spaces (to the next tab stop, matching the indent width used elsewhere) or advance to the next tab stop in the fitter; at minimum replace control bytes (`< 0x20`) with a visible placeholder so they are never emitted raw. Sanitize `file.path` similarly before it reaches `fitCell`/`appendCell`.

**[F15] Diff lines beginning `++ ` / `-- ` misparsed as file headers** — `src/diff.zig:280-291` _(correctness)_
The `+++ `/`--- ` header matchers run unconditionally, **before** the `else if (current_header != null)` hunk-content branch. Inside a hunk, an added line whose content is `++ x` renders as `+++ x` and a deleted line `-- x` as `--- x`; these are intercepted, the diff line is silently dropped, and `file.path` (or `old_path`) is overwritten with the line's content. The corrupted path poisons review-state keys, comment anchoring, file lookup, and the per-line stable id. Realistic triggers: email `-- ` signature separators, committed `.patch`/`.diff` files, markdown rules, diffs-of-diffs. (Verifier note: the patch *fingerprint* is computed over raw bytes and is **not** poisoned, contrary to the original claim; only path-keyed state corrupts. Narrow trigger plus recoverable in-memory-only scope put it at medium.)
**Fix:** Gate the `diff --git`/`new file`/`+++ `/`--- `/rename/copy/`Binary` matchers on `current_header == null` (header lines only appear before the first `@@`), e.g. `else if (current_header == null and util.startsWith(line, "+++ "))`.

**[F16 / F27] `mergeOrAppendFile` leaks the incoming file's hunks slice on every merge** — `src/git.zig:308-320` _(memory)_
_F16 and F27 are the same leak and are merged._ The merge branch allocates `merged_hunks`, `@memcpy`s elements of both `existing.hunks` and `incoming.hunks` into it, frees `existing.hunks`, and frees `incoming.path`/`old_path`/`language`/`patch_fingerprint`/`patch_text` — but never frees the `incoming.hunks` slice backing array (from `toOwnedSlice` in `parseFilePatch`). The elements are moved, so only the backing array (`len * @sizeOf(DiffHunk)`) leaks. Hit routinely in working-tree mode when a file is changed in both index and work tree (it appears in both the `diff` and `diff --cached` passes), and in the untracked merge path. No test exercises `mergeOrAppendFile`. (Verifiers note `loadSnapshot` runs once per process — not in a refresh loop — so the leak is one-time and OS-reclaimed at exit; severity is low, F27's rating.)
**Fix:** Add `allocator.free(incoming.hunks);` in the merge branch alongside the other `incoming.*` frees. Do **not** `deinit` the elements (ownership transferred). Add a unit test merging two parsed patches for the same path.

**[F17 / F22] Height predictor `wrapAnsiTextLineCount` drifts from renderer `wrapAnsiTextWithWidths`** — `src/tui.zig:898-947` _(correctness / simplicity)_
_F17 (the correctness consequence) and F22 (the duplication root cause) describe the same defect and are merged._ The two hand-synced wrap implementations track break points differently: the renderer carries a `previous_was_space` break point pinned to the first space of a run; the counter just overwrites `break_visible_start` on every space. They compute different carry widths and disagree on rendered line count for inputs with consecutive spaces interleaved with code-break chars. The counter consistently **under-counts**, so `visualRowHeight` under-budgets and the real render produces more rows, clipping the bottom row or mis-positioning the cursor/scroll. The project's own committed fuzz test "DIFF wrap count matches wrap alloc len" (tui.zig:3231-3267) already **fails** (531 mismatches on a clean checkout). Mismatches concentrate at small wrap widths reachable only in split view on narrow terminals with deeply-indented delimiter-dense code — not in stacked view.
**Fix:** Eliminate the duplication: have `visualRowHeight` call a single shared wrap core that returns only a count, so height and render can never diverge (accept the extra allocation, or factor the loop into one routine parameterized to emit segments or just count). Keep/repair the existing fuzz test as a regression guard.

**[F18] `fillViewportAtBottom` sums visual heights of ALL rows below scroll every frame** — `src/tui.zig:1966-1982` _(performance)_
Called from `ensureCursorVisibleInLayout` on every render, its first statement (1973) computes `visualHeightBetween(scroll_row, view.rows.len)`, which iterates every row from `scroll_row` to EOF (no early-out) calling `wrapAnsiTextLineCount` on each. The subsequent fill loop is viewport-bounded, but the initial sum is O(rows-to-EOF) — the exact O(n) cost the recent "O(n) scroll" commit removed from the cursor scan but left here. On a large diff with the cursor near the top, every keypress scans to EOF.
**Fix:** Cap the initial sum at `body_height`: walk forward from `scroll_row` accumulating `visualRowHeight`, stopping as soon as the running total reaches `layout.body_height`. This bounds the work to ~`body_height` rows.

**[F19] Whole `FileView` rebuilt from scratch on every keypress and again on every render** — `src/tui.zig:2066-2068` _(performance)_
`currentView()` unconditionally calls `tui_view.buildFileView()`, which walks all hunks/lines of the active file and allocates two `ArrayList`s (plus a per-hunk visibility array in fold mode), with no caching. A plain cursor move builds the view twice per keypress (input handler + `render()`); a fold toggle builds it three times. Combined with F18, every keypress scales with whole-file size. (Human-paced single `readEvent` per keypress keeps it at medium; only large diffs make it user-visible.)
**Fix:** Cache the built `FileView` in `State` keyed by `(active_file, mode, fold_mode, folds-generation)`. Invalidate only on file switch, view/fold-mode toggle, or fold add/remove; cursor/scroll moves reuse the cached view.

**[F20] Untrusted diff/source content written to the terminal without stripping control bytes** — `src/tui_text.zig:9-32` _(robustness)_
`DiffLine.text` is duped verbatim from git output (only trailing `\r` trimmed) and flows through `renderCodeText` → `wrapAnsiTextWithWidths` → `fitCell` to stdout. Only `'m'`-terminated SGR is special-cased; any other control byte — bare `\x1b`, BEL, backspace, `\x1b[2J`, OSC like `\x1b]0;…\x07` or **OSC52 clipboard** — reaches the terminal verbatim. A file under review can therefore inject cursor-movement, screen-clear, title-set, or clipboard sequences just by being diffed; comment body/author/path echoed from the store (cli.zig `printCommentsText`) take the same path. This is the broader root cause behind F13/F14.
**Fix:** When emitting code/comment text, replace control bytes (`< 0x20` and `0x7f`) with a visible placeholder (caret notation or U+FFFD) and forward only recognized ESC sequences (SGR). A single sanitize pass over `line.text` before highlighting/wrapping closes both the injection and the unterminated-ESC corruption.

**[F21] `atomicWrite` calls `renameAbsolute` on a relative path when HOME/XDG_STATE_HOME are unset** — `src/store.zig:541-549` _(robustness)_
`stateBaseDir` falls back to `.` when both env vars are unset, making `comments_path`/`states_path` relative. `createDirPath`/`createFileAbsolute` resolve against cwd and succeed, but `renameAbsolute` begins with `assert(path.isAbsolute(...))`, so in Debug/ReleaseSafe (the default) the first save panics instead of returning a graceful `StorageWriteFailed`. (Verifiers split medium/low: the trigger requires both `HOME` and `XDG_STATE_HOME` unset — `env -i`, minimal container, bare cron/systemd — which is rare; impact is a bounded panic, no data corruption.)
**Fix:** Resolve `repo_dir` to an absolute path in `stateBaseDir`/`init` (realpath the cwd when falling back to `.`), or use the cwd-relative rename API (`Dir.cwd().rename(io, tmp, path)`) in `atomicWrite`. Prefer absolute stored paths so all `*Absolute` APIs stay consistent.

### Low

The 42 low-severity findings are grouped by theme. Each is real but bounded; most are OOM-only leaks, dead code, or cosmetic issues.

**OOM-only error-path leaks / errdefer-coverage gaps** (memory) — all trigger only under allocation failure, after which the process typically exits:
- **[F29]** `stable_line_id` (and duped text) leak in the diff-line branch — `src/diff.zig:353-362`. **Fix:** add `errdefer allocator.free(stable_id);` after the allocPrint, and capture the duped text into a local with its own errdefer before constructing the struct.
- **[F31]** `joinArgs`/`jsonEscape` leak the `ArrayList` buffer on OOM — `src/util.zig:59-64, 68-87`. **Fix:** add `errdefer out.deinit(allocator);` after `var out … = .empty;` in both.
- **[F32]** Owned `rows` slice leaks if `changes.toOwnedSlice` fails in `buildFileView` — `src/tui_view.zig:146-151`. **Fix:** capture `rows` into a local with its own errdefer before taking `changes` ownership.
- **[F37]** `reapplyStyleAfterResets` leaks its `ArrayList` on OOM (hot path, inconsistent with peers) — `src/tui.zig:1136-1149`. **Fix:** add `errdefer out.deinit(allocator);`.
- **[F39]** `render()` leaks its output buffer on mid-render OOM — `src/tui.zig:359-406`. **Fix:** add `errdefer out.deinit(allocator);` after `var out … = .empty;`.
- **[F51]** `addComment` leaks `comment_id` and earlier dupes if a later field dupe fails — `src/store.zig:207-228`. **Fix:** register `errdefer self.allocator.free(comment_id);` right after allocation; build the `Comment` field-by-field with individual errdefers (same anti-pattern in `setReviewState`).
- **[F52]** `setReviewed` leaks the new `ReviewState` dupes and risks a dangling `self.states` (use-after-free/double-free) on the `append`/`toOwnedSlice` OOM path — `src/store.zig:164-177`. **Fix:** build into a local with errdefer; `toOwnedSlice` into a temp and free the old `self.states` only after the new slice is obtained (free-after-commit).
- **[F59]** `highlight` (`line_starts`/`spans_by_line`) leaks when `entries.append` fails in `SyntaxCache.get` — `src/syntax_cache.zig:80-89`. **Fix:** after `build` succeeds, replace the source-only errdefer with one that deinits the whole `highlight` (avoid leaving both active to prevent a double-free of `source`). _(Same line as F6's secondary leak.)_
- **[F60]** Inner `spans_by_line` slices leak if `toOwnedSlice` fails mid-loop in `syntax_query.build` — `src/syntax_query.zig:75-86`. **Fix:** track `built` count and free `spans_by_line[0..built]` in the errdefer.
- **[F61]** `mergeOrAppendFile` leaks intermediate buffers (`merged_patch`/`merged_hash`/`merged_fingerprint`) and the consumed `incoming` file on OOM mid-merge — `src/git.zig:295-323`. **Fix:** add errdefers for the intermediate buffers; have `mergeOrAppendFile` deinit `incoming` on its own error paths (or free remaining parsed files including `incoming` in the caller).

**Malformed-input robustness (corrupt store / hand-fed patch — checked panic in safe builds)** (robustness):
- **[F23 / F63]** _(duplicates, merged)_ Integer-overflow panic on per-line counter increment for adversarial `@@` start values near u32 max — `src/diff.zig:311-340`. Reproduced as `thread panic: integer overflow` at diff.zig:333. **Fix:** use saturating increments (`old_line +|= 1`) or widen the counters to u64 and clamp on store.
- **[F24]** `jsonInt` `@intCast`/`@intFromFloat` panics on out-of-range `start_line`/`end_line` from a corrupted `comments.json` — `src/store.zig:514-522`. **Fix:** clamp before casting (`if (i < 0 or i > maxInt(u32)) default else @intCast(i)`; analogous for `.float`) so corrupt loads default gracefully.
- **[F55]** `syntax_query.build()` does not enforce `max_file_size`; `@intCast(source.len)` would panic for a ≥4 GiB source — `src/syntax_query.zig:42-56`. Unreachable via the only caller (512KB cap). **Fix:** add a defensive `if (source.len > maxInt(u32)) return error.SourceTooLarge;` at the top of `build()`.
- **[F57]** Unguarded `@intCast(source.len)` to u32 in `parse`/`Query.init`; safety net lives only in `syntax_cache.zig` — `src/tree_sitter.zig:32` _(ffi)_. **Fix:** guard the cast inside the FFI binding so it is safe regardless of caller/optimize mode.

**Correctness nits** (correctness):
- **[F25]** `displayWidth` over-counts combining marks (should be 0) and under-counts emoji (should be 2) — `src/tui_text.zig:46-61`. Cosmetic truncation/column drift; cursor math is `@max(…,1)`-guarded. **Fix:** add a zero-width category and extend width-2 ranges to supplementary-plane emoji/CJK (a vendored/generated wcwidth table is the robust option).

## 4. Systemic Patterns

1. **By-value "move" without canceling errdefers (the dominant root cause).** Zig has no destructive move, so passing an owning struct by value leaves the source variable — and its `errdefer .deinit` — still armed. `loadSnapshot` consuming `repo`/`target` (F2–F4, F7, F8), `addComment` committing a value into `self.comments` (F5/F10), and the syntax `source` buffer crossing `get()`→`build()` (F6) are all the same mistake: **two owners, two frees**. The fix discipline is uniform — once ownership transfers, disarm or never-arm the donor's errdefer, ideally via a `committed`/`moved` flag or by making the consumer dupe.

2. **"Free old before committing new" and "fallible op after commit" ordering.** F5/F10, F51, F52 all free or commit state *before* the last fallible operation, so an error unwinds into a half-updated structure. The systemic fix is **commit last**: perform all fallible allocation/serialization first, mutate owned state only once nothing else can fail.

3. **Single source of truth violated by hand-synced copies.** The wrap algorithm exists twice (F17/F22) and already disagrees — caught by the project's own failing fuzz test; comment JSON is serialized twice with divergent shapes (F50); width is computed with three different policies (F14, F25, F54); grammar counts/status strings are hardcoded and drift (F41, F42). Duplication here is not cosmetic — F17 silently corrupts viewport math.

4. **Untrusted bytes (git output, argv, store files) flow unsanitized to the terminal and to JSON.** Control bytes and escapes reach the terminal (F13, F14, F20), non-UTF-8 reaches agent JSON (F48), and corrupt store values reach unchecked casts that panic (F24). A single normalization layer at each trust boundary (terminal-out, JSON-out, store-in) would close most of these.

5. **Unchecked narrowing casts / arithmetic on externally-derived sizes.** `@intCast(usize→u32)` in the FFI binding (F55, F57) and per-line `u32` increments from parsed headers (F23/F63) panic in safe builds. Validate at the boundary (or use saturating/checked ops) rather than relying on a distant caller's cap.

6. **Error/teardown paths are systematically under-tested.** The bulk of memory findings live on error paths the suite never exercises (no failing-allocator harness, no merge fixtures, no live-TTY input). The testing allocator catches nothing it never runs.
